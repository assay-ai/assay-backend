# Runbook: Proof-of-reserves breach

**Signal:** `reserve_health_breach` / `reserves_breach` — `vault_balance < Σ liabilities`.
**Severity:** CRITICAL, unconditional page — the only golden signal that pages unconditionally.
**Where it's decided:** `ReconciliationService` (`src/modules/settlement/services/reconciliation.service.ts`),
run by `ReconciliationJob` (`src/modules/settlement/jobs/reconciliation.job.ts`) every 5 minutes
(`RECONCILIATION_CRON = '0 */5 * * * *'`), **only in the scheduler process** — one run per
deployment, not one per API replica.

This document assumes you got here from an alert. If you got here without one, first check whether
alerting actually reached you — see **§0** below before anything else.

## §-1. Which chain? Establish this FIRST — the remedies do not overlap

The alert carries `asset`, and an asset belongs to exactly one chain
(`src/modules/chains/ports/asset-registry.ts`). Read the chain off the asset before anything else,
because the two chains are short in different places, are refilled by different people, and behave
differently while they are short:

| | `solana:*` | `eip155:*` |
|---|---|---|
| what holds the money | a Squads multisig vault + its ATA | `X402Escrow` itself — the contract IS the vault |
| how a shortfall is fixed | fund the Squads vault (a multisig proposal + approvals) | send USDG to the escrow proxy — an ordinary ERC-20 transfer, no multisig |
| what "control unverified" means | the vault ATA's authority is not the derived PDA, or the PDA is not owned by the Squads program | the ERC-1967 implementation slot, `CONFIG.admin()` or `ASSET()` disagrees with `EVM_DEPLOYMENTS` |
| can buyers still take money out? | no — withdrawals go through this platform, and `isFrozen` refuses them | **yes.** `withdraw()` is `msg.sender`-only, pays `msg.sender`, and is NOT pause-gated |

That last row is the one to act on. **On EVM the freeze does not stop buyers exiting.** Every buyer
can keep calling `withdraw()` directly against the escrow contract for as long as the platform is
short, and nothing this codebase can do will stop them — `setPaused` on chain does not gate
`withdraw()` either, deliberately (a paused contract that trapped user funds would be worse). So an
EVM shortfall gets worse on its own, and the useful clock is how long refunding takes rather than
how long investigating takes. Fund first, investigate second.

**`isFrozen` is per asset, and therefore per chain.** A CRITICAL run on `eip155:46630` freezes
withdrawals of USDG and leaves Solana untouched, and vice versa. Do not "freeze everything" by hand:
there is no such switch, and a freeze that crosses chains is deliberately not representable.

**A control failure is not a shortfall.** If the findings say `RECONCILIATION_FAILED` rather than
`RESERVES_BREACH`, the pass never read a balance at all — `assertVaultControl` runs first and the
row's `vault_balance` is `NULL`. On EVM that most often means somebody upgraded the escrow, or
rotated `X402Config.admin`, without updating `EVM_DEPLOYMENTS`. Check the deployment record
(the `deployments/<chainId>.json` record that assay-evm's `script/verify-deployment.sh` reads; the record is generated by a deployment and is not published in that repository) before assuming money is
missing.

## §0. Is the alert actually reaching anyone?

`ReconciliationService.raise()` emits through `ALERT_PORT`, which today resolves to a
`FanOutAlertSink` over `LoggingAlertSink` (always) and `WebhookAlertSink` (only if configured — see
`src/config/observability.config.ts`). If nobody has set `ALERT_WEBHOOK_ENABLED=true` and
`ALERT_WEBHOOK_URL`, **a reserves breach only reaches the process logs.** That is the exact failure
mode alerting exists to close — if you are reading this runbook because someone happened to be
tailing logs rather than because a page fired, that is itself an incident: get the webhook
configured before you close this one out.

## 1. Halt payouts and withdrawals

**Not automatic in the sense the phrase implies — it is a read, not a switch.**
`ReconciliationService.isFrozen(asset)` returns `latest.severity === 'CRITICAL'` off the most recent
row in `reconciliation_runs` for that asset. The caller that gates on it:

- `WithdrawalService.assertNotFrozen` (`src/modules/settlement/services/withdrawal.service.ts`) —
  throws `SettlementErrors.withdrawalsFrozen` (`SETTLEMENT_WITHDRAWALS_FROZEN`, HTTP 409) from
  `requestWithdrawal`.

So once the CRITICAL run lands, withdrawals are already frozen — you do not need to flip anything for this
step. Confirm it did:

```sql
SELECT asset_id, severity, difference, started_at
FROM reconciliation_runs
WHERE asset_id = '<caip-19 asset, e.g. solana:.../token:EPjF...>'
ORDER BY started_at DESC
LIMIT 1;
```

If `severity` is not `CRITICAL` here but you believe there is a breach, the freeze has not engaged —
escalate as a reconciler bug, do not wait for the next tick.

`TreasuryVaultService.checkReserves` (`src/modules/settlement/services/treasury-vault.service.ts`)
can re-derive the same inequality live. `proposeWithdrawal` and `proposePayoutBatch` no longer
exist, so the reconciliation freeze above is the one that gates withdrawals.

Handled by step 0 if configured. If it is not, page manually now — do not wait to finish this

## 3. Identify the divergence

`ReconciliationService.run()` writes one row with a `findings` array
(`ReconciliationFindingCode` in `src/modules/settlement/ports/reconciliation.types.ts`). Read it
off the row you queried in step 1 — `findings` is stored as-is on `reconciliation_runs.findings`.
Each code means a specific thing in this codebase, not a category:

| Finding | What it actually means here |
|---|---|
| `RESERVES_BREACH` | `vault (chain) < journal total`. Either funds left the vault ATA without a ledger entry, or a liability was recorded against money that never arrived. **Zero tolerance** — `RECONCILIATION_SHORTFALL_TOLERANCE_ATOMIC = 0n`. |
| `SNAPSHOT_DRIFT` | `account_balances` (the cache every hot-path read hits) disagrees with the journal it is folded from. The vault can still cover the total — this can fire with `RESERVES_BREACH` clean. Means **every balance read since the drift began was wrong**; the journal (`ledger_entries`) is authoritative, never the snapshot. |
| `NEGATIVE_BOOK` | One of `agentLiabilities` / `openHolds` / `providerPayable` / `platformFees` folded negative — impossible through the ledger's own row-locked debit paths and Postgres `CHECK` constraints, so this means a write bypassed both. Named in `details.book`. |
| `UNEXPLAINED_SURPLUS` | WARN only, not this incident — the vault holds more than the ledger accounts for (uncredited deposit or a stray transfer). Investigate separately, does not gate anything. |
| `RECONCILIATION_FAILED` / `RECONCILIATION_BLIND` | The chain read itself failed, 3 times running (`RECONCILIATION_MAX_CONSECUTIVE_FAILURES`). Not a money breach — a "nobody has checked in 15 minutes" breach. Fix the RPC/vault-control path first; the money question is unanswered until then. |

**The doc's third diagnosis line — "open holds vs intent states" — has no automated check.**
`checkBooks` only tests that `openHolds` (part of the folded total) isn't negative; it does not cross
`ledger_holds` against `payment_intents.status` for a stuck-hold bug. If `RESERVES_BREACH` and
`SNAPSHOT_DRIFT` are both clean and you still suspect a stuck hold, do it by hand:

```sql
SELECT h.id, h.amount, h.status, h.created_at, i.status AS intent_status
FROM ledger_holds h
JOIN payment_intents i ON i.id = h.intent_id
WHERE h.status = 'OPEN'
ORDER BY h.created_at ASC
LIMIT 20;
```

An `OPEN` hold against an intent that is already terminal (`SETTLED`/`REFUNDED`/`FAILED`) is the
stuck-hold signature.

## 4. Never "correct" the ledger by hand — and know before you need it that this codebase has no button for the alternative either

The doc's prescribed fix is *"find the missing or extra entry and write a compensating entry with a
cause."* **There is currently no supported way to do that in this codebase.**
`LedgerEntryType` (`src/modules/ledger/ports/ledger.types.ts`) has no `ADJUSTMENT`-shaped member, and
`LEDGER_ENTRY_EFFECTS` (`src/modules/ledger/domain/ledger-entry-effect.ts`) is a
`Record<LedgerEntryType, LedgerEntryEffect>` — TypeScript enforces it is total, so a new entry type
cannot be introduced without touching both files and re-deriving its sign/direction, which is
engineering work, not an incident action. `LedgerService.appendNow` (the one generic journal-append
method) exists but taking it during a live incident to misuse an unrelated entry type is exactly the
kind of unreviewed write this reconciler exists to catch on the *next* pass. **Do not do it.**

What that means in practice: find the missing/extra entry, write down what it should have been (id,
amount, direction, cause), and treat *adding a real compensating-entry mechanism* as the fix this
incident produces — not something to route around live. That is deferred work; if you are the one
handling this incident, it is also the seam the next engineering task on the ledger domain should
pick up.

## 5. Resume only after the invariant holds for 3 consecutive checks

There is no manual re-run endpoint or admin trigger for the reconciler — the next pass happens on
the next 5-minute tick, automatically, in the scheduler process. "3 consecutive checks" = **15
minutes** of `severity != 'CRITICAL'` on `reconciliation_runs` for the asset:

```sql
SELECT started_at, severity, difference
FROM reconciliation_runs
WHERE asset_id = '<asset>'
ORDER BY started_at DESC
LIMIT 3;
```

All three rows below `CRITICAL` (and no gap — check `started_at` deltas are ~5 minutes, not evidence
the job stopped running) is the resume signal. `isFrozen` re-reads on the very next call, so nothing
else needs to be flipped back — withdrawals un-freeze themselves the moment the row says
so.
